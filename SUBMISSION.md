# PatchTrial — evidence, not vibes, for AI-generated code

## The problem

Coding agents usually stop when their own patch passes the repository tests. That is weak evidence:
an incomplete or subtly wrong patch can pass an incomplete test suite.

## The idea

PatchTrial is a model-agnostic coding harness that puts a generated patch on trial. After producing
and testing a candidate, it generates plausible semantic counterfeits—wrong implementations that a
reasonable coding agent might have written—and asks whether the same tests detect them.

If a valid counterfeit survives, PatchTrial proposes a focused test-only patch, proves the test still
passes for the correct candidate, and reruns the surviving counterfeits. A patch is accepted only
when the evidence reaches a minimum quantity and fault-category diversity.

> Ordinary agents ask whether their patch passes. PatchTrial asks whether the tests would notice if
> the patch were wrong.

## Why this is a harness, not a prompt wrapper

- autonomous repository mapping and issue investigation;
- bounded context and action budgets;
- constrained, validated file and command tools;
- evidence-backed reproduction state;
- candidate verification and adversarial patch trials;
- test-only evidence strengthening;
- automatic clean-baseline rollback on failure;
- portable OpenAI-compatible transport for DeepSeek and Qwen;
- machine-readable, hash-bound proof artifacts and aggregate scorecards.

## Judge quick start

```bash
git clone https://github.com/pragya238/PatchTrial.git
cd PatchTrial
make setup
make test
make demo
```

The deterministic demo uses no API key and exercises the complete candidate → counterfeits →
surviving faults → stronger test → accepted-evidence loop.

For an evaluator-provided model and repository:

```bash
export AI_API_KEY="<provided>"
export AI_BASE_URL="<provided>"
export AI_MODEL="<provided>"
export AI_PROVIDER="deepseek"   # or qwen
export TARGET_REPO="/path/or/https-git-url"
export TASK_FILE="/path/to/issue.txt"
make run
```

Only `AI_API_KEY` is secret. No code changes or committed configuration are required.

## Verdict policy

- Candidate tests must pass.
- At least three valid counterfeits must run by default.
- At least two distinct fault categories must be represented.
- Every valid counterfeit must be killed.
- Otherwise the result is rejected, needs stronger tests, or is explicitly inconclusive.

PatchTrial never labels 1/1 as “high confidence.” It reports kill rate and evidence confidence as
different metrics.

## Safety and recovery

The target must begin as a clean Git repository. Paths cannot escape the repository; commands do not
use a shell and executables are allowlisted; patches must pass `git apply --check`; tool output is
bounded; repository processes do not receive the model API key. Unexpected failures restore both
tracked and untracked changes to the clean baseline. Tests execute repository code, so official
evaluation should still use an isolated environment.

## What the proof contains

Each JSON report records the target baseline commit, candidate-diff SHA-256, non-secret model
configuration, evidence thresholds, candidate result, all valid and invalid trials, fault categories,
strengthening decisions, token counts, command timings, and output tails.

## Honest limitations

Counterfeits are generated by the configured model, so they do not prove semantic correctness or
replace hidden tests and review. PatchTrial instead makes weak evidence visible, challenges it, and
refuses to overstate confidence. The evaluation plan compares the full loop with a candidate-only
baseline on the same DeepSeek/Qwen task matrix.
